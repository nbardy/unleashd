# T03 — Fix B1: channel seat turns must not carry owner authority

Branch: `fix/b1-seat-authority` (from `lean/integration` @ ab47223), commit **59ea29a**. Not merged, not pushed.

## Root cause (confirmed)
- `server/src/buddies/channel-responder.ts` `runReply` sent every seat turn with `{ origin: 'owner_input', inputId: trigger.id }`. That included follow-ups reached through `considerThreadPost` → gate `<yes>` → `reply`, whose trigger is often a Buddy-authored post.
- `server/src/conversations/runtime.ts` `spawnForMessage` sets `hasOwnerControls = turnInput.origin === 'owner_input' && …`. It then sets `UNLEASHD_BUDDY_OWNER_CONTROL_AVAILABLE=1` and attaches `buddyOwnerMcpServers` (`unleashd_owner`: configure_team and owner document writes).
- Result: another Buddy's thread post could start a turn that held owner authority.

## Change
- **runtime.ts**
  - `TurnInput` gains a precise variant, `'buddy_post'`: a seat answering a post that another Buddy wrote. `SeatTurnInput = 'owner_input' | 'buddy_post'` is exported, and `sendSessionRelativeMessage` takes it.
  - `contextForInput` is now an exhaustive switch on origin:
    - `buddy_post` keeps the seat's `owner_thread` audience. A different scope fails the package's audience fence and resets the seat session.
    - Unlike `owner_input`, it does **not** lift `delegatedByBuddyId` / `allowedBuddyOperations` / `coordinationRunId`, because only the owner gets a new claim.
  - Owner controls are still granted only to `owner_input`, so `buddy_post` never gets the owner MCP.
- **runtime.ts (queue)**: the chat-admission queue used to keep only owner inputs, so any other input came back from the queue as `'unknown'`. Every seat turn goes through that queue, so `_queuedOwnerInputs` became `_queuedInputs: Map<string, TurnInput>`. Without this, a `buddy_post` turn would run under the workspace audience and lose the seat's session.
- **channel-responder.ts**: the new `seatTurnInput(store, triggerId)` re-reads the trigger post from the store by id and switches on `author.kind`:
  - `owner` → `owner_input`
  - `buddy` → `buddy_post`

  The origin never comes from prompt text. A missing post throws, which becomes a visible `reply_failed`. A comment at this site names B1.
- **Doc**: `product/buddies/CHANNEL_CONVERSATIONS_2026-09-23.md` §2 now describes the rule and names the guard test.
- Owner @mentions work exactly as before: `owner_input`, with the same context, owner MCP and claim reset.

## Test
The new test is in `server/test/channel-seat-continuity.test.ts`: "a seat turn holds owner authority only when the owner wrote its trigger post". It runs the real responder, the real runtime (queue, run admission, audience check), the Buddies integration and an on-disk BuddiesStore. Only the provider process is faked. The harness also gained `issueOwnerControlCapability` and a configurable gate.
1. The owner @mentions Lead. The turn has `unleashd_owner` (with the trigger id) and `OWNER_CONTROL_AVAILABLE=1`.
2. Designer (a Buddy) replies in the thread, the gate says respond, and Lead runs a follow-up. That turn has **no** `unleashd_owner` and `OWNER_CONTROL_AVAILABLE=0`. It still has the Buddy MCP, resumes seat session `native-1`, and posts its reply.
3. The owner mentions Lead again. The owner MCP is back and the session still resumes.

Mutation check: with the Buddy case switched back to `owner_input`, the test fails with `AssertionError: Buddy-authored trigger: no owner MCP`. The resume assertion also covers the queue change.

## Notes for the rewrite
- A Buddy-triggered seat turn still reads the seat's `owner_thread` memory audience. That is deliberate: the same thread text already reaches owner-triggered seat turns, and CORE_DESIGN says inherited audience is preserved. Only *authority* is withheld. Whether channel seats should use an `owner_thread` scope at all is a separate audience question (§8.6).
- To run tests in a fresh worktree: `git submodule update --init`, `pnpm install --frozen-lockfile --offline`, `pnpm --dir vendor/agent-cli-tool run build`, and `pnpm --dir shared run build`.
