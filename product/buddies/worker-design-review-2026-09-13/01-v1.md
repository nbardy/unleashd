# Worker system — v1

September 13, 2026. Assistant proposal prepared at the owner's request. This is
the first design pass, preserved before reflection. It is not an implemented API
or owner acceptance of the details below.

The design should let a person discuss work with a Buddy, leave that Buddy to
manage it, and return to inspect results. The person should not have to nurse
execution receipts, restart helpers after timeouts, or decide whether a message
secretly starts work.

## Product objects

| Object | Responsibility | Lifetime |
|---|---|---|
| Buddy | Named identity, role, model preferences, memory and relationships | Until explicitly retired |
| Worker | An ordinary Buddy with temporary-worker mode and one parent | Across a coherent body of related tasks and their feedback |
| Task | Desired outcome, owner, criteria, checklist, status and evidence | Until completed or cancelled; history remains |
| Mail | Addressed correspondence and replies | Immutable delivery history |
| Document | Named, audience-scoped versioned content: soul, memory, shared brief or note | Independent of execution; notes append, editable documents use revisions |
| Conversation | Human-initiated discussion with a Buddy | Independent of background work and its limits |

Worker is a mode of Buddy, not a second identity implementation. Task maps to
today's `owned_projects` resource; existing checklist rows remain checklists.
Workspace/repository and an owned work item must stop sharing the UI name Project.

The parent relation comes from the canonical manager edge. Creating a Worker
creates its identity and edge atomically. Standing direct reports remain ordinary
Buddies. Workers are hidden from the general roster and shown under their parent.
Retirement retains their history and requires settled work and stopped processes.

## Execution model

Each Worker has one autonomous execution lane. A durable binding connects the
Worker, its related task IDs, permitted context, provider session, current solo
session and original resource authorization. Multiple tasks do not mean multiple
concurrent writers. Messages enter that same lane.

A lead has a short background coordination lane for reading reports, planning,
review and dispatch. Call these coordination turns in implementation and omit a
new Desk object. The lead can also have human conversations; background work
cannot inject automatic turns into them or consume their background admission.

A context binds an identity to an audience and provider session. Reuse it through
process exits and required reviews. Start another compatible context if provider
or audience changes; retain the Worker identity. Never copy a parent's private
conversation or memory merely because it created the Worker.

Execution requests and attempts remain distinct. A request can queue and have
multiple attempts. An attempt has one private claim, process owner, captured
configuration and terminal receipt. A completed provider turn need not complete a
Task. A stopped or failed attempt does not destroy the Worker.

## Coordination protocol

1. The parent creates Tasks with outcomes and evidence requirements.
2. `create_worker` creates a temporary Buddy under the parent's staffing grant.
3. `assign_work` attaches related Tasks and starts its first bounded session.
4. The Worker checkpoints and updates task evidence while executing.
5. `report` delivers useful progress or a request for review to the parent.
6. The parent inspects the evidence and records its review on the Task.
7. `continue_worker` explicitly grants the next bounded session, or the parent
   revises the plan, stops the approach, or retires the Worker when finished.

`mail` stores correspondence without executing a model. `prompt` asks an ordinary
Buddy for one short coordination turn in an authorized context and returns a
receipt. Waiting for its result is an observation choice; it does not turn a
queued prompt into a running one. A Worker's continuing task execution is managed
by assign/continue, not an open message with a mandatory terminal reply.

Reports compose existing task evidence, checkpoints and Mail. No Report table or
second completion status is necessary. A report that needs a decision also queues
a linked parent coordination turn. Routine progress Mail can wait in the inbox.
The parent must be able to review even after the Worker has exhausted its current
session or its old provider process has exited.

## Check-ins and limits

One resolver supplies effective policy to preview, admission, claims, timers and
both user interfaces. It separates these controls:

| Control | Meaning |
|---|---|
| Check-in interval | Time between useful progress observations |
| Maximum solo session | Admitted working time before required parent review |
| Total authorized effort | Cumulative allocation ceiling across the original work and its descendants |
| Optional calendar deadline | Expiration even during waits |
| Attempt watchdog | Process/liveness failure bound |
| Admission | Concurrent occupancy and queue/rate eligibility |
| Permissions | Authorized operations and effects |

Check-ins never reset the solo session. Queued or drained waiting does not consume
admitted solo time; running tools do. Retries and task switches preserve elapsed
time. Required review checkpoints, reports, drains, and pauses the Worker. Only
the parent can grant a new session within its delegated remaining authorization.

At the check-in interval the host forks the Worker context, asks a bounded
reporting-only execution to summarize progress, sends that result to the parent,
and ends the reporting execution. The original Worker continues. The reporter
cannot implement, allocate, renew, or spawn. Record snapshot time and checkpoint;
pending tools and missing evidence remain explicitly unknown.

Reserve coordination effort so the final review can happen. Deduplicate periodic
reports and required review notifications. Cancellation revokes capabilities
before drain and wins over late messages and continuation decisions.

## MCP presented to each role

Existing exact-read and revisioned resource operations should remain recognizable.
These are proposed names, not tools callable today.

| Surface | Tools |
|---|---|
| Work and recovery | `get_current_work`, `new_task`, `update_task`, `checkpoint`, `get_runs`, `stop`, `retry_run` |
| Knowledge | `get_document`, `update_document`, `recall`, `remember_note` |
| Communication | `get_inbox`, `get_message`, `mail`, `prompt`, `report` |
| Team observation | `list_buddies`, `get_team_state`, `get_capabilities` |
| Worker management | `create_worker`, `assign_work`, `continue_worker`, `retire_worker` |
| Granted administration | `create_buddy`, `set_relationship`, `get_profile`, `update_profile`, `retire_direct_report`, `get_automations`, `set_automation` |

Workers receive scoped work/knowledge/communication tools, but no independent
Worker-management or schedule-activation authority by default. Leads additionally
receive management tools. Explicit staffing/profile/document grants still apply;
visibility is not permission. A Worker explicitly allowed to manage a team uses
its existing lane for review and delegation. Reporting and memory-maintenance
executions get distinct restricted tool sets, not ordinary employee authority.

All mutations use stable idempotency keys; revisioned changes require current
revisions. Tool results distinguish saved state, delivered Mail, queued execution,
running attempts and verified completion. Failures explain the reason and who
can resolve it. Descriptions state the actual side effect rather than embedding a
second workflow manual in every tool.

## What goes away

- New managed work rooted in `send(delivery.kind="work")` and its open reply.
- Worker's identity or provider context being recreated because a Task or turn ended.
- The public `send` boolean/variant routing burden, and `continueFrom` as an
  execution destination selector for new work.
- Self-addressed work messages as the normal way a lead runs implementation.
- Separate new delegation/review/assignment records duplicating Task outcomes.
- Repeated limit calculations and defaults in consumers.
- Automatic background delivery into human chat; ordinary roster clutter from Workers.

Existing history, private claim enforcement, task evidence, owner grants,
checkpoints, provider adapters, document audiences and one WS bridge remain.
Old requests retain their stored time semantics. Do not revive exhausted requests
or reinterpret past failed receipts when migrating.

## Acceptance and open implementation details

The first journey is one Worker with two related Tasks: start, automatic check-in,
pause for required review, parent continuation, same context, accepted outcome.
Repeat through duplicate delivery, restart, cancellation and full Worker capacity.
Human conversation must remain usable throughout.

Before implementation, tighten the exact assign/continue/prompt contracts, task
acceptance versus Worker retirement, atomic report/wake writes, and the provider
fork guarantee. Explicitly measure whether the reporting execution can be
restricted as intended. No runtime tests or model-cost savings are claimed by
this design document.
