# Reflection on v1

September 13, 2026. Self-review of the saved [v1](01-v1.md), not an independent
review or runtime evaluation. The owner requested this reflection before v2.
The artifact manifest pins the exact v1 bytes.

V1 has a coherent product model, but it is not yet a clean operating protocol.
These are the changes I would require before handing it to implementers.

## 1. Too many execution verbs

`assign_work`, `continue_worker`, `prompt`, and `retry_run` all ask the runtime to
make execution eligible. An agent must select a verb based on historical state,
while each route must preserve the same context, policy, claim and cancellation
rules. This invites the same drift that the design is meant to remove.

**V2:** one `prompt` command with explicit start, continuation and recovery input
variants. It returns one request receipt. A continuation requires the current
session revision; recovery names the failed attempt and inspected effects. These
variants cannot silently allocate a new root account. Keep the old services as
compatibility adapters while old requests drain.

Keep `create_worker` separate and inert. Creating identity is useful before
execution, and combining it with prompt would make creation's side effects
surprising. But create identity plus its parent relationship in one transaction;
do not require a second `set_relationship` ceremony for every temporary helper.

## 2. Reports still ask the Worker to keep three records in sync

V1 says update Task, checkpoint, then send Report. A crash between those calls
can leave useful work saved without the notification required to get it reviewed.
Adding a Report table would merely add another record to synchronize.

**V2:** `report` is a deliberate transaction over existing Task updates,
checkpoint and durable delivery intent. Its `checkpoint` variant replaces the
standalone checkpoint tool. Progress does not wake the lead; blocked work and
review candidates do. Required solo-session review is generated by the host even
if the Worker never manages to call report. Report is a command, not a sixth
product object.

## 3. A reply cannot own the work

Current installed `background-work.js` discovers work from a message's run policy,
looks up one `buddy_project_id`, derives waiting from child `expects_reply`
messages, and returns a final disposition through that message. V1 correctly
rejects that coupling but does not finish the replacement.

**V2:** a durable execution request connects an authorization, compatible
context and task references. Mail is optional evidence of why the request exists.
Task state determines completion. Requests retain their own execution outcome.
Neither a reply nor a completed provider turn marks the Task done. No new
Assignment, Batch, Review or Report resource is exposed.

## 4. One lane needs a real database constraint

V1 says one Worker lane while contexts can multiply. Today's admission also
checks conversation occupancy and configurable per-Buddy active runs. Merely
choosing a preferred conversation ID does not enforce one Worker writer.

**V2:** a Worker-wide active execution fence across all its background contexts,
retained until process exit and event drain. Task handoff and audience/provider
changes cannot admit a second writer. Short reporting executions never own this
work lane and have no implementation authority.

## 5. A batch can cross a privacy boundary

The installed knowledge resolver uses one active project/workspace audience, not
an arbitrary union of task contexts. Giving a Worker multiple tasks does not make
their private histories mutually shareable. Using `taskIds[0]` as the audience
would create an implicit, order-dependent leak or access failure.

**V2:** a batch shares one explicit existing audience and authorization. Related
child tasks normally share their parent Task's audience. Task IDs do not broaden
that audience. Incompatible work can remain owned by the same Worker but executes
in a separate context, serially, after current execution drains. Reuse the same
Worker through feedback and related tasks; retire it explicitly after obligations
settle. No automatic reuse for unrelated future work.

## 6. Native fork is an unverified dependency, not the requirement

`session.ts` supports harness-specific native or emulated forking, and can reject
unsupported providers. That establishes neither an atomic snapshot of an active
session nor replacement of inherited tool authority. A raw fork may retain
instructions, private content or tools intended for implementation.

**V2:** specify the behavior as a bounded report from a timestamped, permitted
snapshot. The safe baseline is a fresh reporting process with a supplied snapshot
and no action tools, then host-controlled internal Mail delivery. Native fork is
an optimization only after proving snapshot completeness, scope and capability
replacement. The existing restricted memory-review runner is a useful structural
precedent, not proof that the new reporter works. Reporting does not recursively
trigger memory review or another report.

## 7. Required review must not depend on courtesy

V1's call sequence can still depend on the Worker choosing to stop and on the
lead seeing a message in time. Timer expiration must leave a durable management
obligation, not a closed failed request plus a hopeful email.

**V2:** the host commits session hold plus a retained cause plus notification
intent together, revokes work effects, drains, then admits one lead review. A
continuation transaction consumes the current hold revision and records the
decision/allocation/next eligible request together. Old causes remain handled
history. A fresh cause after the snapshot is not swallowed by an older decision.

## 8. Routine mail should not stop all related work

Today's managed parent waiting is derived from open child response obligations.
Under that rule, a nonblocking peer question can suspend an otherwise productive
batch. V1 does not specify what replaces that dependency.

**V2:** Mail has no execution wait semantics. A Task blocked on a response records
that specific cause on the Task. Other runnable Tasks can continue in the same
solo session. A lead coordinating several Workers never holds a provider slot
waiting for them; results queue the next short coordination turn.

## 9. Task acceptance and retirement are different decisions

Completing the first Task must not retire a two-Task Worker. Submitting a candidate
must not imply that the parent inspected it. Renaming `accepted_by` would be wrong:
today it records the recipient accepting an assignment, not a reviewer accepting
an artifact.

**V2:** Task candidate and acceptance evidence are recorded on the versioned Task.
The Worker submits review; the parent accepts the exact candidate revision using
`update_task`. No new Review store. `retire_buddy` accepts a Worker only after open
Tasks, pending decisions, queued inputs and active processes are settled. Incoming
late Mail remains deliverable to history and redirects attention to the parent;
it never reactivates the retired Worker.

## 10. “One limits system” is not a license to change old units

The current request duration is elapsed since first admission; the proposed solo
clock excludes drained waiting. These are observably different. The current
foreground admission still counts global/per-Buddy occupancy, so foreground
independence is a needed change rather than something already guaranteed.

**V2:** versioned policies and explicit legacy/new request semantics. One package
resolver owns admission and accounting; consumers display its decision. New work
uses separate work/coordination capacity with foreground independence from those
quotas. Existing hard timeouts and immutable failed receipts remain unchanged.
Total active-provider seconds, solo seconds and calendar time are named units,
not a claim about dollars. Unobserved helper work cannot be called fully metered.

## 11. The tool count alone does not prove simplification

V1's table contains 30 distinct tools. Today's normal resource catalog contains
25 before additional policy restrictions. V1 adds several concepts the agent must
learn and does not clearly pay for them with removals.

**V2:** a 25-tool union, with 12 in an ordinary Worker turn and 18 in ordinary lead
coordination. Administration and detailed diagnostics are explicit additional
profiles. Counts are proposed catalog sizes, not performance evidence. No generic
`do_everything` action bag hides extra operations. The worthwhile reduction is in
protocol decisions: one execution command, one report command, one completion
authority, and no message lifetime masquerading as work lifetime.

## 12. The migration must retire implementations, not just names

Replacing a public tool name while leaving two new-work executors and scattered
policy calculations would make the code larger without making the system cleaner.

**V2:** list removal conditions for the managed-message path, legacy completion
helpers, standalone checkpoint/retry public tools, duplicate defaults and direct
scheduled implementation. Preserve old readers/adapters until compatible history
and active requests no longer need their write path. Build the package from the
verified installed source commit; do not overwrite it from the stale main checkout.

## Review conclusion

The product direction survives this reflection. V2 should strengthen the runtime
boundaries and reduce the choices required of agents. It should not introduce a
new Worker store, Report service, review queue database, human-chat executor or
arbitrary task graph to achieve that result.

Whether v2 performs better still needs execution evidence: correct tool selection,
successful report/review/continuation, cancellation and privacy boundaries, and
coordination overhead. This self-review establishes a more precise proposal;
it does not establish measured implementation success.
